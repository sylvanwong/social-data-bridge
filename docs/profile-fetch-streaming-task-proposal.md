# 博主作品采集大任务增量处理方案

## 背景

当前流程是：前端提交全部主页链接，后端任务全部采集完成后，前端通过任务状态接口轮询，完成后再分页拉取结果并写入飞书多维表格。

一次提交 2060 个主页时，后端实际运行约 69 分钟；前端轮询约 6 分 40 秒后停止，因此页面会停留在最后一次收到的进度（例如“已获取第 218 页”），但后端任务最终可能仍然成功。

Mongo 文档大小（本次约 438 KB）不是主要瓶颈。主要问题是任务耗时、前端固定轮询时限，以及任务结果无法在前端中断后可靠恢复。

## 推荐目标

- 后端采集过程中持续产出结果，前端按小批次增量写入飞书。
- 前端不依赖固定的 6 分钟轮询上限，而是根据任务进度和心跳判断任务是否仍在运行。
- 前端刷新、网络中断或飞书写入失败后，可以从上次确认位置继续处理。
- 不直接使用 Redis `POP` 作为唯一结果消费方式，避免数据被取出后因前端失败而丢失。

## 推荐流程

```text
前端创建 task_id
  -> 后端 Worker 逐个采集主页
  -> 每完成一批结果，持久化并更新任务进度
  -> 前端轮询任务状态
  -> 前端按 cursor 拉取已完成结果
  -> 前端写入飞书成功后确认 cursor
  -> 任务完成且结果追平后结束
```

## 接口建议

### 1. 任务状态

保留现有任务状态接口，但增加明确的进度字段：

```json
{
  "task_id": "xxx",
  "status": "running",
  "total": 2060,
  "processed": 218,
  "succeeded": 210,
  "failed": 8,
  "available_count": 210,
  "result_cursor": "218",
  "heartbeat_at": 1786592200
}
```

字段含义：

- `processed`：后端已经处理的输入主页数。
- `succeeded` / `failed`：成功和失败数量。
- `available_count`：当前可供前端拉取的结果数量。
- `result_cursor`：结果流的最新位置。
- `heartbeat_at`：后端最近一次实际推进任务的时间。
- `status`：至少区分 `running`、`completed`、`failed`。

### 2. 增量结果

```http
GET /social/api/v1/feishu/social/task/results?task_id=xxx&cursor=218&limit=20
```

```json
{
  "items": [],
  "next_cursor": "238",
  "has_more": true,
  "task_status": "running"
}
```

每次最多返回固定数量（例如 20 条），避免一次响应携带全部任务结果。

### 3. 写入确认

前端完成一批飞书写入后确认游标：

```http
POST /social/api/v1/feishu/social/task/results/ack
```

```json
{
  "task_id": "xxx",
  "cursor": "238"
}
```

结果应包含稳定的 `result_id` 或 `sequence`，便于重试和去重。

## Redis 使用建议

Redis 可以用于 Worker 队列、实时通知或结果缓存，但不建议让前端直接执行破坏性的 `POP`：

- 浏览器关闭或飞书写入失败时，结果可能已经从 Redis 删除。
- ack 请求丢失时，前端无法判断哪些数据已经安全写入。
- 无法支持任务重试和断点续传。

建议结果至少持久化到 Mongo 的任务结果集合，按 `task_id + sequence` 建索引；Redis 只作为加速层。若使用 Redis Stream，应保留消息和消费游标，直到任务完成并超过重试保留期。

## 前端轮询策略

- 上一次状态请求完成后再发起下一次请求，避免并发积压。
- 有进度变化时 2 到 3 秒轮询一次。
- 连续无进度时逐步退避，最长可到 30 秒。
- 只要 `processed` 或 `heartbeat_at` 持续变化，就继续等待。
- 只有超过约 5 到 10 分钟没有任何心跳或进度变化，才提示任务异常。
- `status = completed` 后，仍需等结果 cursor 追平、飞书写入完成，再显示最终成功。

## 需要后端评估的事项

- 结果使用 Mongo 持久化、Redis Stream，还是其他可重放队列。
- `processed` 的统计单位是主页数、作品页数，还是结果条数，需统一命名和语义。
- 任务失败后是否保留已成功结果，以及是否允许从 cursor 继续。
- 结果保留时间、重复任务幂等规则和单任务最大链接数。
- 是否通过 SSE/WebSocket 推送进度，或继续使用前端轮询。

## 过渡方案

在增量结果接口完成前，可以先将前端固定轮询超时改为“按任务心跳判断”，并允许后端任务继续运行；但这只能解决前端过早停止等待，不能解决任务结果无法断点拉取的问题。
