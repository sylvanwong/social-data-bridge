# 附件上传批次 3 / 5 张对比测试

在飞书插件首页进入「附件耗时对比」，输入一个已完成的小红书任务 ID，点击「开始对比测试」。当前 API Key 必须能读取此任务。默认取相同的前 80 条作品，全部作品必须有封面。可改为 40 的整数倍，最多 400 条。

每页固定写入 40 条，每次新建四张测试表，各写入相同样本：第一轮上传批次 3 → 5，第二轮 5 → 3。两组使用默认作者作品字段及封面附件，下载并发保持 3，使用已有后端缩略图代理。测试结束后可删除这些测试表。

复用 `useSocialData.createAndWriteData`，每批记录：

- `downloadMs`：整页封面下载墙钟时间，包括下载并发池排队以及转成 File。
- `uploadMs`：所有分组 `batchUploadFile` 调用的累计时间。
- `writeMs`：`addRecords` 调用时间。
- `totalMs`：单批完整处理时间，还包含字段获取、校验、格式设置、单元格构建；表创建和首次字段初始化不计入。
- `attachmentCount`、`attachmentBytes`：成功下载图片数和字节数。

固定样本只读取一次，结果读取不计时。这是对下载/上传/写表三阶段的批量大小对比，不包含后端采集等待或分页 API 耗时。正式作者作品和关键词搜索导入每页最多 40 条，小红书封面采用下载并发 3、每 5 张批量上传，整页处理后再批量写表。

结果表为两轮累计，JSON 报告包括每轮、每批明细与测试表 ID。不导出业务内容、图片 URL、附件 token 或 API Key。图片下载失败、token 数量不匹配、记录写入数量异常会结束测试，不自动新建表重试；失败前已完成的批次仍保留。

只有报告 `completed=true` 且两组记录数、图片数、下载字节总量一致时才比较。建议查看两轮各自总耗时，确认上传批次的优势是否稳定；交换顺序只能减轻缓存影响，不能消除客户端或 CDN 缓存、网络和飞书服务波动。

本地检查：`node scripts/test-xhs-cover-download.mjs` 校验下载并发、代理选择、失败释放并发槽及 20/40 张附件 token 映射；`npm run build` 检查构建。实际飞书 SDK 性能必须由插件内测试测量，本地检查不提供实际提速结论。

## 边下载边上传测试

性能测试页面现使用 `attachmentPipeline: true`：下载并发仍为 3，每 3 / 5 张一组，组内下载完成就上传，后续组继续下载。SDK 上传只有一个批次在执行，整页 token 就绪后才写表。作者作品和关键词搜索业务导入也启用此流程，固定上传批次为 5；测试页继续对比 3 / 5 张。

报告增加 `attachmentMode: pipeline`、`uploadBatchSize` 及每批 `attachmentPipelineMs`（从开始下载到全部上传结束的实际墙钟时间）。下载与上传有重叠，二者不能相加；请用相同样本的 `totalMs` 与之前报告比较。分组会增加上传调用次数，是否提速须实测。

下载失败时最多尝试 3 次（首次加两次重试），仍失败则显示作品 ID、期望/成功图片数和最后错误原因。`downloadRetryCount` 记录成功批次中额外发起的下载尝试次数，重试排队和等待时间计入下载及总耗时。失败报告中的 `currentBatch` 标识失败发生的轮次、上传批次大小和页次。重试后成功不等于网络环境一致，比较时需结合重试次数。
