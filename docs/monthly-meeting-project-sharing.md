# 社媒数据助手飞书插件：项目月会分享稿

> 适用场景：项目月会、阶段复盘、向团队介绍插件的产品价值和工程演进。
>
> 分享设置：面向技术、产品等混合听众；以 15 分钟为基准，可压缩到 10 分钟或扩展到 20 分钟。后续 PPT 无既定模板，重点用场景、前后流程对比和少量示意图表达。
>
> 说明：本文基于当前仓库代码、`docs/` 中的接口说明和 Git 历史整理。涉及后端接口的内容，区分为“前端已实现的对接行为”和“后端需要遵守的协议约定”，不把方案文档等同于线上能力。

## 一、项目是什么

### 1. 一句话介绍

社媒数据助手是一个运行在飞书多维表格中的数据采集与写入插件：用户在表格里配置 API Key、数据来源和输出方式，插件调用社交平台数据服务，把作者、作品、评论、热榜、关键词、短剧等数据整理后写入飞书表格。

它不是单纯的“数据查询页面”，而是一条完整的数据工作流：

```text
用户配置采集任务
  -> 请求社媒数据服务
  -> 轮询/增量读取任务进度
  -> 按游标分批获取结果
  -> 校验飞书字段并转换数据类型
  -> 新增或更新多维表格记录
  -> 支持定时执行、恢复和停止
```

### 2. 帮助客户解决什么问题

客户通常需要从多个平台持续收集内容数据，再用于选题、竞品分析、账号运营、内容复盘或业务报表。原始流程往往是手工复制链接、逐个平台查询、再整理到表格，成本高且容易漏数据。

插件把这些重复步骤收敛到飞书工作空间内，主要解决四类问题：

| 客户痛点 | 插件提供的能力 | 直接收益 |
| --- | --- | --- |
| 多平台数据入口分散 | 支持抖音、小红书、快手、微博、B 站、知乎、TikTok、YouTube、X、今日头条等平台配置 | 统一采集入口，减少切换和人工整理 |
| 数据量大，手工写表耗时 | 批量链接、关键词、作者主页、评论和热榜采集，分批写入 | 从“人工搬运”变成可重复的数据流程 |
| 每个客户的表结构不同 | 选择字段、同名自动匹配、字段映射、自动创建字段、写入方式配置 | 插件适配已有业务表，不强迫客户重建表格 |
| 长任务容易超时或中断 | 增量结果、进度轮询、断点恢复、停止任务 | 大任务可观察、可恢复，降低失败后的重复成本 |

### 3. 当前功能版图

- 音视频：作品详情、作者信息、作者作品、关键词搜索、评论列表、视频文案摘要。
- 内容扩展：热榜、主页短剧、小红书下载、链接转附件。
- 任务能力：立即执行、定时任务、进度展示、停止任务、增量写入和刷新后恢复。
- 表格能力：新建表格或使用现有表格，选择输出字段，支持文本、数字、单选、多选、日期时间、链接和附件等类型。
- 数据质量：字段类型校验、数字和日期格式化、标签选项自动补齐、按作品或评论 ID 更新或新增、批量写入。

## 二、项目演进和遇到的问题

### 1. 从“能写入”到“适配真实表格”

早期版本重点是把接口返回的数据写入飞书。真实客户使用后，问题逐渐从“接口能否返回数据”转变为“数据能否稳定进入客户已有的表”。因此演进重点包括：

- 2026-04：支持使用现有表格，开始面对历史字段和客户自定义表结构。
- 2026-06：支持选择输出字段、批量链接、多平台和链接转附件；数字字段增加格式化。
- 2026-07：标签默认使用多选，同时兼容文本；支持从表格选择和手动输入两种入口。
- 2026-08：新增字段映射和写入方式，解决同一份数据写入不同业务表的问题。
- 2026-08 以后：采集任务改为增量读取；关键词、评论、作者作品等页面陆续支持停止任务。
- 2026-09：字段映射扩展到热榜、短剧、评论等页面，并增加并发控制、封面附件等能力。

这个演进说明：插件的核心难点不只是接入更多平台，而是维护“外部数据模型”和“客户表格模型”之间的稳定边界。

### 2. 案例一：客户已有的表格，为什么不能直接写？

**场景与问题**：客户已经有业务表格，作者列叫“博主账号”，标签列还是文本，并且已经配置了视图和统计。直接要求客户使用插件默认字段，会增加迁移和维护成本。

这个问题有两个层面：一是“写到哪一列”，通过字段映射解决；二是“按什么格式写”，通过字段类型兼容解决。两者共同组成适配客户表格的能力。

**历史依据**：`1e5bf28`（2026-04-16，支持使用现有表格）、`4ff88ce`（2026-04-20，字段类型验证）、`de7ea53`（2026-07-01，标签默认多选且兼容文本）、`e9910cb`（2026-08-25，新增字段映射和写入方式）。

#### 按客户的字段类型转换数据

飞书字段类型有明确约束，但社媒接口返回的数据并不稳定。例如：

- 标签可能是数组、空值或以空格分隔的字符串；
- 作者名称、平台、作品类型可能适合单选，也可能是客户希望自由录入的文本；
- 主页链接在部分历史表中已经建成文本，而新表更适合链接类型；
- 早期版本已经创建了文本字段，强制升级字段类型会破坏客户已有数据。

因此代码中不是简单地把一个来源字段绑定到唯一类型，而是定义“允许的兼容类型”：

| 来源字段 | 允许的目标字段 | 写入处理 |
| --- | --- | --- |
| 作者名称、平台、作品类型 | 文本或单选 | 文本直接写入；单选写入选项名称 |
| 标签 | 文本或多选 | 文本写入拼接后的标签；多选自动创建缺失选项并写入选项 ID |
| 主页链接 | 文本或链接 | 根据目标字段类型写入字符串或链接值 |
| 点赞数、评论数、时长等 | 数字 | 使用数字字段和整数格式化，避免字符串无法参与统计 |

这样做的取舍是：表结构保持兼容，客户可以逐步规范化，而不是为了插件升级一次性迁移所有数据。代价是写入前必须做字段类型校验和按类型归一化，代码复杂度更高。

#### 将来源字段映射到客户目标列

“同名字段自动写入”适合新建表格，但不适合真实业务表。客户可能把“作者名称”命名为“博主账号”，把“作品链接”命名为“原文地址”，或者把多个来源的数据合并到一张统一表中。

字段映射解决的是来源字段和目标列名称解耦的问题：

```text
来源字段 key：nickname（作者名称）
          -> 目标字段 ID：fld_author（博主账号）
```

当前规则是：

1. 有显式映射时，优先按目标字段 ID 写入；目标字段不存在则报错，避免误写到其他列。
2. 没有映射时，按字段名称和历史别名匹配。
3. 仍未找到时，新建同名字段（显式映射字段不自动补列）。
4. 映射和写入方式按“插件类型 + Base + 目标表”保存，切换目标表不会互相覆盖。
5. `upsert` 查重始终使用原始作品 ID 等稳定 key，不能因为列名映射而改变查重逻辑。

字段映射本质上是一个适配层，让插件可以嵌入客户已有的数据模型，而不是要求客户迁就插件字段名。

**分享落点**：客户可以在已有业务表上逐步接入插件，保留原有列名和可兼容的字段类型。PPT 可用“作者名称 → 博主账号、标签 → 文本/多选”展示来源与目标的关系。

### 3. 案例二：任务跑了一个小时，页面为什么早就不动了？

**历史依据**：`f974cc1`（2026-08-11，作品详情和作者信息改为每条获取成功后立即写入）、`5cb9852`（2026-08-17，采集任务更新为增量读取）。具体大任务案例记录于 [博主作品采集大任务增量处理方案](./profile-fetch-streaming-task-proposal.md)。

历史方案是：前端提交全部输入，等待后端任务完成，完成后一次性分页读取结果并写入。这个方案在小任务上简单，但长任务会暴露明显问题。

一个实际案例是：一次提交 2060 个主页，后端运行约 69 分钟；前端固定轮询约 6 分 40 秒后停止等待。此时后端可能仍在工作，但页面已经停留在最后进度，任务结果也无法可靠接续。

因此引入了增量任务模型：

```text
后端持续产出结果
  -> 前端按 cursor 读取一小批
  -> 写入飞书成功
  -> 保存 cursor、目标表 ID、已写入数量
  -> 继续轮询和读取
```

前端的 `useIncrementalTask` 会保存任务 ID、结果游标、已写入数量、最近进度、心跳和轮询间隔。在同一个 Base 重新打开对应页面时，会尝试恢复保存的任务；成功恢复还依赖后端结果仍可读取、目标表可访问等条件。批次写入抛出错误时，游标不会提前推进，轮询会在重试窗口内重新处理该批结果。

轮询也不是固定频率死等：有进度时约 2 秒轮询；连续没有变化时逐步退避，最长约 30 秒；超过约 10 分钟没有进度或心跳才认为任务异常。这样既减少请求，又避免把“后端仍在正常工作”误判成超时。

这里有一个重要的可靠性原则：必须先确认飞书写入成功，再保存/推进结果游标。否则可能出现结果已经被读取但尚未写入，刷新后无法找回的情况。

**分享落点**：让用户更早看到结果，降低中断后从头处理的成本。这些改动不代表后端采集从 69 分钟缩短了，也不能把刷新恢复理解为所有情况下都能保证绝不重复。PPT 可对比“全部采集完再写入”和“分批采集、分批写入、记录游标”两种流程。

### 4. 案例三：同一份数据重复获取，为什么表里越来越乱？

**场景与问题**：同一条作品今天点赞 100，明天点赞 150。日常运营表希望更新原记录；如果每次都新增，就会堆积重复记录，影响统计。但如果要保留每日快照，新增记录又是合理需求。因此写入方式要由业务用途决定。

**历史依据**：`e9910cb`（2026-08-25，引入作品更新或新增）、`0ff7011`（2026-09-14，修正评论更新或新增）。

目前提供两种方式：

| 写入方式 | 同一条数据再次获取时 | 适合场景 |
| --- | --- | --- |
| 始终新增（append） | 新增记录 | 保存采集快照、追踪每次结果 |
| 更新或新增（upsert） | 按稳定 ID 查找，存在则更新，不存在则新增 | 维护作者作品库、评论库等当前状态数据 |

这里的难点不仅是“判断 ID 是否相同”。评论修复提交中的旧实现直接把飞书读取到的 ID 转成字符串；当单元格以数组或对象形式返回时，可能无法与接口中的评论 ID 正确匹配。新实现增加了 ID 归一化，并改进了以下处理：

1. 按原始作品 ID 或评论 ID 判断同一条数据，不依赖标题、作者名或映射后的列名。
2. 同一批结果先去重；缺失必要 ID 的记录跳过并提示，避免错误合并。
3. 在任务内缓存目标表的 ID 索引，避免每一批结果都重新扫描整张表；新增成功后更新索引。
4. 更新和新增分批执行，控制单次写入规模。

这个案例也与断点恢复有关：允许重试后，同一批结果可能再次被处理，必须同时考虑重复写入。“更新或新增”可以降低重复记录风险，但飞书写入和本地游标保存不是同一个事务，当前实现不能宣称所有异常下都能保证恰好写入一次；“始终新增”本身也允许产生重复记录。

**分享落点**：数据采集要同时考虑数据质量和长期维护成本。PPT 可展示同一个作品 ID 第二次执行时，两种写入方式的不同结果。

### 5. 案例四：用户点击停止后，为什么不能立刻结束？

**历史依据**：`2d30b2e`（2026-09-14，评论支持停止任务）、`7ce1b2a`（2026-09-14，作者作品和关键词支持停止）、`69f5470`（2026-09-20，其他页面支持停止）。

“立即执行”并不意味着用户必须等待任务自然结束。实际使用中，用户可能发现链接输错、范围选大、数据不再需要，或者只是想先查看已经写入的部分。

中断能力解决三个问题：

- 控制成本：不再继续发起不必要的平台请求。
- 控制范围：停止后续采集或处理，明确已经产生的结果仍可能继续写入。
- 控制体验：用户可以结束当前任务，而不是关闭插件或刷新页面等待不确定结果。

当前分两类处理：

1. 后台采集型任务（作者作品、关键词、评论等）：前端已实现点击停止后调用取消接口，展示“正在停止”，继续读取和写入已持久化结果，并识别 `cancelled` 终态。后端协议要求 Worker 在可中断边界停止新增请求，保留已产生的结果，确认不再产生新结果后进入终态。后端具体执行效果需联调验证，不能仅凭前端代码确认。
2. 前端直接处理型任务（例如批量下载/写入）：设置停止标记，等待当前网络请求或当前记录处理完成，不再开始下一条，避免在半个请求中强行打断造成状态不一致。

所以“停止”不是简单地把定时器清掉，而是要区分“停止生产新数据”和“排空已经生产的数据”。

**分享落点**：停止功能需要同时兼顾用户控制和已有结果的完整性，不等同于撤销已写入数据。PPT 可展示“运行中 → 正在停止 → 已有结果写完 → 已停止”的过程。

### 6. 其他值得分享的工程问题

#### 数据写入类型和格式

早期数字字段用文本创建，导致点赞数、评论数等无法可靠统计；后续改为数字字段并设置整数格式化。日期字段统一按飞书日期时间格式写入。标签多选还需要先检查并补齐选项，再写入选项 ID。

#### 并发请求和结果顺序

长任务中如果状态轮询、结果读取和写入同时并发，容易出现游标乱序、重复写入或竞态。增量任务 composable 使用 `inFlight` 控制同一任务只允许一个轮询链路，批次完成后才推进游标。

另一个独立问题是重复提交：`1552896`（2026-09-14）增加 `isSubmitting`，在异步字段校验、读取来源链接等准备阶段就锁定提交入口，而不只依赖任务运行后的 `loading`。这个改动防止用户在准备阶段连续点击创建多个任务，可作为案例三的补充。

#### 附件下载失败

封面等附件需要下载、必要时走代理，并设置超时。单个附件失败时跳过该附件并继续写入其他字段，避免一张图片的问题拖垮整批数据；批次级写入失败则保留游标，交给任务重试。

#### 单表容量与自动建表（备选案例）

`6e15e3d`（2026-05-11）增加了写入失败后自动创建新表、继续写入的兜底流程。但历史代码对写入异常统一尝试建表，尚未严格区分容量、权限、网络或配置问题。适合作为“异常处理还可以怎样改进”的例子，不宜表述为已经成熟的容量治理方案。

#### 定时任务（产品价值补充）

`39c0b2e`、`5c5ae90`、`7ea5b3c` 在 2026 年 7 月分别引入作者信息、作品详情和作者作品定时任务。适合用于说明项目从一次性采集走向持续更新，不必占用四个问题案例的篇幅。

## 三、我对项目的改进建议

### 1. 近期：稳定性和可观测性

1. **统一任务状态模型**：所有长任务统一使用 `queued/running/cancel_requested/succeeded/failed/cancelled`，统一 `processed/total/heartbeat_at/written_count` 字段，减少每个页面各自解释状态的分支。
2. **统一增量任务组件**：作者作品、关键词、评论目前已经共享相似逻辑，后续可将取消、恢复、结果排空、错误重试和进度文案进一步抽成统一任务控制器。
3. **幂等写入和结果保留**：后端结果应按 `task_id + sequence/result_id` 持久化，前端确认写入后再 ack；取消、失败或刷新后仍能读取已产生结果，避免依赖一次性的 Redis POP。
4. **任务历史页**：展示最近任务、状态、输入范围、成功/失败数量、停止原因和最后更新时间，用户不必只依赖当前页面提示。
5. **错误分层**：区分鉴权失败、平台采集失败、字段配置错误、网络超时、飞书写入失败和附件失败，并给出可操作的处理建议。
6. **补充监控指标**：记录任务耗时、每批写入耗时、接口错误率、重试次数、取消响应时间和单条附件失败率。Sentry 已接入，后续可补充任务 ID、插件类型等非敏感上下文。

### 2. 中期：产品化和效率

1. **任务模板**：把平台、字段、目标表、映射、写入方式和执行范围保存为可复用模板，降低重复配置成本。
2. **预览和校验**：执行前预览少量样例，提前显示字段类型不兼容、必填字段缺失、映射重复和目标表权限问题。
3. **失败重试中心**：允许只重试失败的输入或失败批次，而不是重新执行整个任务；展示失败原因和原始链接。
4. **增量同步策略**：为作者作品、评论等场景提供“首次全量、后续按更新时间同步”的默认策略，减少重复采集。
5. **更多触发方式**：在定时任务之外，评估按表格新增链接触发、Webhook 触发或工作流触发。
6. **大数据量体验**：增加任务队列、并发度限制和配额提示，对单次输入量、结果保留时间和单表容量做显式提示。

### 3. 长期方向

插件可以从“社媒数据采集工具”发展为“飞书内的内容数据工作台”：采集只是入口，后续可以连接清洗、标签体系、内容分析、竞品监测和报表视图。优先顺序建议是：

```text
可靠采集与写入
  -> 可配置的增量同步
  -> 统一任务与失败管理
  -> 数据质量和分析能力
  -> 面向团队的模板、权限和协作
```

核心判断标准不是功能数量，而是客户能否稳定地把一次性采集变成长期运行的数据资产。

## 四、月会分享建议结构（10–20 分钟）

以 15 分钟为基准，面向混合听众，四个案例按“场景与问题 → 原因 → 方案 → 价值”展开，提交编号留作讲稿依据，不必逐条出现在 PPT 正文中。

| 环节 | 时间 | 重点 |
| --- | --- | --- |
| 项目定位、客户价值和功能版图 | 3 分钟 | 谁在使用、解决什么重复劳动，用一张插件或结果表截图说明 |
| 案例一：适配客户已有表格 | 2 分钟 | 字段映射与类型兼容，展示来源字段到目标列的关系 |
| 案例二：长任务增量与恢复 | 3 分钟 | 2060 个主页的历史案例、前后流程对比、写成功再推进游标 |
| 案例三：重复数据与写入方式 | 1.5 分钟 | 同一作品的点赞变化，展示 append 与 upsert 的不同结果 |
| 案例四：停止任务与结果收尾 | 1.5 分钟 | 停止新增采集，处理已有结果，再结束任务 |
| 复盘和后续方向 | 3 分钟 | 优先讲统一任务模型、失败重试和任务历史，其余建议简述 |
| 收尾 | 1 分钟 | 从一次性导入走向持续维护的数据表 |

压缩到 10 分钟时，项目介绍 2 分钟、四个案例合计 5 分钟、后续方向 2 分钟、收尾 1 分钟，省略备选案例和代码细节。

扩展到 20 分钟时，可增加约 3 分钟完整操作演示和 2 分钟交流：输入作者主页、配置目标表和映射、观察分批写入、恢复未完成任务、停止并收尾。长任务和断点恢复可准备录屏或截图，不依赖现场等待大任务完成。

## 五、可直接使用的总结

这个项目最有价值的地方，不只是接入了多少个平台，而是把不稳定的外部数据采集，转化成了适配客户表结构、可观察、可恢复、可停止的飞书数据流程。项目后续应继续围绕可靠性、可配置性和长期自动化展开，让客户从“偶尔导一次数据”逐步过渡到“持续维护一张可用的数据表”。
